## Macro and micro routing

**INSPECTED CODE.** `models/marco_router.py:38–101` projects graph node features to width 256, adds binary visited-state embeddings, thresholds pair distances at five metres with self-loops, applies two graph-attention blocks, then pools with a projected mean instruction embedding. `models/nav_model.py:254–268` forms the instruction mean with its attention mask and sets one macro distribution on all LoRA layers. `models/moe_lora.py:91–110` computes a per-token linear-softmax micro distribution and mixes it with the macro distribution using beta 0.3. Each LoRA expert applies down/up projections, scaled by alpha/r; seven attention/FFN projections are targeted by the launch scripts.

**Paper/code differences.** The forward path loops over **all** experts, with no top-two activation mask (`moe_lora.py:106–110`), whereas paper p. 8 states Top-K=2 routing. This is dense mixture evaluation in the inspected source, not demonstrated sparse computation. Before the macro router receives `gmap_embeds`, visited-node representations have been zeroed (`nav_model.py:171–192,261–267`). The router can still use visited indicators and graph topology, but those visited nodes no longer carry their original visual/position/step vectors in this path. No benchmark effect was measured.

**Release blockers.** `nav_model.py:95,109` contains `import *` inside `__init__`; the executed compile-only check reports `SyntaxError: import * only allowed at module level` at line 95. The constructor calls `inject_moe` and `freeze_except_moe` (`100,119`), while the supplied helper names are `inject_moe_lora` and `freeze_all_except_moe_lora` (`moe_lora.py:115,187`). A repository-wide search located no aliases for the requested names. Independently, `GNNLayer.forward` unpacks `B, N = H.shape` (`marco_router.py:28`), although the caller forms `H` with shape batch × nodes × 256 (`81–91`). This is a static dimension inconsistency; its runtime was not executed. Together these prevent direct reproduction from the unmodified pinned source.

## Supervision, workload and consolidation

The intended navigator training alternates teacher-forced imitation and sampled-state supervised rollouts (`tasks/agents/mp3d_agent.py:507–525`). Both supervise navigation logits with teacher action cross entropy (`736–756`); sampling alone does not make this a policy-gradient loss. `train.py:223` constructs summed CE, `35–115` performs clipped optimizer updates, and `tools/optims.py:34–60` uses AdamW on trainable parameters. The freeze helper, if correctly wired, freezes all weights except expert/router parameters (`moe_lora.py:187–199`); the release blockers mean this is source intent, not a successful training result. Scripts specify rank 16, alpha 32, batch four, lr 2e-5 and five epochs.

**Important discrepancy.** Paper Eqs. 9–10 sum the **fused routing weights** across tokens. The released statistics hook instead recomputes **micro-only** softmax, counts its top-two expert IDs, and replaces both with sentinel -1 when their weight gap is below 0.04 (`tools/momentum/experts_stats.py:61–75,163`). Normalization includes these sentinel counts (`85–97`). Thus the released importance statistic is neither the paper's fused probability workload nor a direct performance-importance measure. The stats launcher selects the current scene's **train** split, despite running through the validation API (`scripts/2_collect_stats.sh:16`); this path is not evidence of held-out label leakage.

`tools/momentum/momentum_update.py:43–64` chooses at most two experts with an additional frequency threshold; sentinel -1 can occupy a sorted position and is skipped. It does not always select exactly two experts. The merge applies 0.6 new + 0.4 old to selected expert weights and 0.6 old + 0.4 new to others (`82–98`), matching the intended direction of Eq. 13 with gamma 0.4. Non-expert parameters, including routers, simply take their new values. No retention guarantee follows from either weighting rule.

## Evaluation and reproducibility limits

`scripts/4_eval.sh` requests the base split plus eight scene splits. `train.py:227–239` evaluates each independently; `tasks/datasets/r2r.py:63–129` computes endpoint SR, oracle SR, path length and SPL. Checkpoints are selected by validation SPL-derived score (`train.py:185–204,263–289`). The inspected evaluator does **not** implement or aggregate the cross-stage BWT/FWT matrix, and a repository-wide search found no such implementation. Consequently it does not resolve paper Eq. 14's FWT baseline ambiguity; published BWT/FWT numbers remain paper evidence. The split configurations contain literal `<scanID>` placeholders and no inspected script constructs or verifies the claimed 80/20 scene partitions. README links external prepared data and requires manual repetition of training/statistics/merge for each scene.

The statistics launcher also contains prose after a backslash continuation (`2_collect_stats.sh:14`), in addition to unset checkpoint/output paths. This is another reason the scripts require repair/configuration, not evidence about the private code used for the paper.

Inspected source ranges: `models/nav_model.py:1–135,142–305`; `models/moe_lora.py` and `models/marco_router.py` complete; both `tools/momentum` files complete; `train.py:35–115,123–307`; `tasks/agents/mp3d_agent.py:500–530,675–778`; `tasks/datasets/r2r.py:1–141`; `tasks/datasets/mp3d_dataset.py:1–75`; `tasks/loaders.py:1–160`; `tools/optims.py` complete; parser routing options; all four launchers, both R2R YAML configs and README. These findings establish release discrepancies and reproducibility limits, not invalidity of the authors' reported experiments.
